# Контракт разработки Weather to DOCX

Статус: обязательный. Этот документ применяется к человеку, кодовому агенту и автоматизированному процессу, изменяющему репозиторий.

## 1. Источники истины

При расхождении сведений приоритет определяется так:

1. актуальная ветка `main` на GitHub;
2. выполняемый код и автоматические тесты;
3. `pyproject.toml` как канонический источник текущей версии;
4. `VERSION`, `weather_to_docx.__version__`, конфигурация, активная документация и релизные маркеры, которые обязаны совпадать с `pyproject.toml`;
5. описания в задачах, PR и отчётах.

Нельзя использовать память агента, старый PR, локальную копию или предыдущий ответ как источник текущего состояния без повторной проверки.

## 2. Протокол начала работы

Перед первой модификацией исполнитель обязан:

1. получить SHA текущей `main`;
2. прочитать текущую версию из `pyproject.toml` и проверить `VERSION`;
3. просмотреть верхний раздел `CHANGELOG.md`;
4. определить затронутые компоненты, документы и тесты;
5. создать рабочую ветку непосредственно от проверенной `main`;
6. зафиксировать в PR базовый SHA и решение по версии: «без изменения» либо «новый выпуск».

Старая ветка не считается пригодной автоматически. Если `main` продвинулась, ветка должна быть синхронизирована и повторно проверена.

## 3. Контракт версионирования

### 3.1. Каноническая версия

Каноническое значение находится в:

```text
pyproject.toml → project.version
```

Остальные текущие представления обязаны совпадать:

```text
VERSION
src/weather_to_docx/__init__.py
.env.example
packaging/weather-to-docx.env
docs/.release-ready
docs/RELEASE_TAG.txt
README.md
CHANGELOG.md
docs/ACCEPTANCE.md
docs/METEOGRAMS.md
docs/RELEASE_STATUS.md
docs/RELEASE_NOTES.md
```

Метаданные адаптеров используют `weather_to_docx.__version__`, а не отдельную строку.

### 3.2. Запрет понижения

Версия не может быть ниже версии в базовой `main`. Понижение допускается только как явно оформленный аварийный откат отдельным решением владельца проекта; при этом откатывается код, а номер опубликованного выпуска повторно не используется.

### 3.3. Когда менять версию

Обычная ветка исправления или разработки сохраняет текущий номер. Номер меняется только при явной подготовке выпуска. Агент не выбирает новый номер самовольно.

При выпуске одновременно обновляются все текущие представления, описание выпуска и верхняя запись `CHANGELOG.md`. Исторические записи не редактируются так, будто они относятся к новому выпуску.

### 3.4. Тег и релиз

Следует различать:

- текстовый ожидаемый тег `docs/RELEASE_TAG.txt`;
- реальный Git-тег в `refs/tags`;
- GitHub Release.

Наличие одного не доказывает наличие других. Утверждать «тег создан» или «релиз опубликован» разрешено только после отдельного чтения GitHub API.

Обязательная проверка:

```bash
python scripts/check-version.py
```

## 4. Контракт веток и PR

- Прямые изменения `main` запрещены для обычной разработки.
- Рабочая ветка создаётся от текущей `main` и содержит только изменения одной задачи.
- PR сначала создаётся как draft.
- В PR указываются базовый SHA, версия до/после, перечень изменений, тесты и известные ограничения.
- Ready for review допускается только после успешных локальных проверок.
- Слияние запрещено, пока хотя бы одна обязательная проверка имеет состояние `queued`, `in_progress`, `failure`, `cancelled` или отсутствует.
- Перед слиянием проверяется, что ветка не отстаёт от `main` и не имеет конфликтов.
- После слияния исполнитель повторно читает `main`, версию и результат слияния.

## 5. Контракт реализации

### 5.1. Поведение и тесты

- Новое поведение сопровождается тестом.
- Исправленный дефект сопровождается регрессионным тестом, который воспроизводил бы прежнюю ошибку.
- Нельзя ослаблять тест только ради зелёного CI без объяснения изменившегося требования.
- Нельзя удалять проверку, документацию или функцию как «лишнюю», не подтвердив это условиями задачи.

### 5.2. DOCX и метеограммы

При изменении генерации документа или графиков обязательны:

- структурная проверка DOCX;
- проверка числа и размеров изображений;
- контроль русских подписей и единиц;
- физический рендер LibreOffice/Poppler, когда инструменты доступны;
- проверка пустых страниц и касания содержимого края;
- контрольный артефакт или тестовый документ.

Основной отчёт не должен снова превращаться в техническую выгрузку. Исследовательские поля допускаются только в явно выбранном специальном режиме.

### 5.3. Научная корректность

- Нельзя сглаживать интервальные осадки как непрерывную величину.
- Нельзя суммировать перекрывающиеся интервалы повторно.
- Нельзя объединять разные ансамблевые системы в один ансамбль без отдельной методики.
- Нельзя выдавать время формирования документа за цикл модели.
- Неопределённость, полнота ансамбля и происхождение данных должны отображаться честно.

### 5.4. Установка и офлайн-режим

Изменение зависимости, точки входа или runtime требует проверки wheel и автономного комплекта. Обновление не должно уничтожать базу, настройки и созданные документы.

## 6. Контракт доказательств и отчётности

Исполнитель не сообщает по памяти:

- текущую версию;
- статус `main`;
- факт слияния;
- зелёный CI;
- наличие тега или релиза;
- число страниц или успешный рендер.

Перед таким утверждением должен существовать свежий проверяемый результат. В итоговом отчёте указываются:

- фактическая версия из `main`;
- merge SHA или SHA последнего коммита;
- конкретные выполненные проверки;
- известные ограничения;
- различие между ожидаемым и реально созданным тегом/релизом.

Если действие выполнить не удалось, это указывается прямо. Убедительное предположение не заменяет результат.

## 7. Обязательные проверки

Минимальный набор перед готовностью PR:

```bash
python scripts/check-version.py
python scripts/check-development-contract.py
ruff check .
pytest
python -m compileall -q src
node --check src/weather_to_docx/static/app.js
node --check src/weather_to_docx/static/reliability.js
node --check src/weather_to_docx/static/compact_report.js
weather-to-docx-verify --deep
```

Для системных изменений дополнительно выполняются wheel и offline bundle. Для изменений DOCX — физический рендер на Python 3.11 в CI.

## 8. Стоп-условия для агента

Агент обязан остановить подготовку к слиянию и устранить проблему, если:

- версия расходится хотя бы в одном активном источнике;
- рабочая ветка основана не на актуальной `main`;
- тест или CI не завершён успешно;
- документ не прошёл структурную либо обязательную визуальную проверку;
- есть неподтверждённое предположение о теге, релизе или установленном runtime;
- изменение удаляет данные или совместимость без миграции и явного согласования;
- результат частичный, а задача описана как полностью завершённая.

## 9. Definition of Done

Задача завершена только при одновременном выполнении всех условий:

1. требования реализованы без скрытого сокращения объёма;
2. тесты добавлены или обоснованно обновлены;
3. версии согласованы;
4. контракт разработки проходит;
5. полный CI зелёный;
6. PR слит без конфликта;
7. `main` после слияния повторно проверена;
8. итоговый отчёт содержит точный SHA и не содержит неподтверждённых заявлений.
