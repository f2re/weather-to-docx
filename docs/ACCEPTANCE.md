# ✅ Приёмка Weather to DOCX 0.2.0

Документ фиксирует проверяемый критерий достижения технической цели проекта: оператор сохраняет несколько координат, выбирает прогностические модели, создаёт одну задачу и получает отдельный DOCX по каждой точке, общий манифест и ZIP. После перезапуска API и worker данные, очередь и результаты не теряются. Установка и обновление выполняются из автономного комплекта без обращения к Интернету.

## 1. Автоматическая приёмка

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -e '.[dev]'

ruff check .
pytest
python -m compileall -q src
weather-to-docx sample --output var/acceptance --hours 24
```

Тест `tests/test_operator_workflow.py` воспроизводит полный пользовательский поток:

1. запускает API и сохраняет две координаты;
2. завершает первый процесс API;
3. повторно запускает API и проверяет постоянный справочник SQLite;
4. создаёт пакетную задачу через HTTP API;
5. завершает API и запускает отдельный worker;
6. повторно запускает API;
7. проверяет два DOCX, `manifest.json` и общий ZIP;
8. открывает каждый DOCX библиотекой `python-docx` и проверяет структуру;
9. проверяет повтор задания и отмену ожидающей задачи.

В тестах не используется Интернет: для воспроизводимости применяется источник `demo`, который явно помечается как синтетический.

## 2. Приёмка реальных источников

Сетевые проверки выполняются на шлюзе или сервере с разрешённым исходящим HTTPS-доступом.

```bash
weather-to-docx sources
weather-to-docx generate \
  --config examples/locations.yml \
  --output var/provider-smoke
```

Для каждой выбранной модели необходимо проверить:

- источник и модель подписаны отдельно;
- время получения и доступное время цикла не смешиваются;
- отсутствующие параметры отображаются как `—`, а не как ноль;
- расчётные ансамблевые величины помечены `*`;
- вероятность осадков сопровождается порогом и числом доступных членов;
- сбой одной модели не блокирует документы по остальным моделям и координатам;
- вторая таблица содержит все нормализованные параметры либо сообщает, что дополнительных полей нет.

Для прямого `noaa_gfs_0p25` дополнительно проверяются ecCodes, выборочный GRIB2, точный цикл и кэш исходных файлов.

## 3. Приёмка интерфейса оператора

```bash
weather-to-docx api --host 127.0.0.1 --port 8080
weather-to-docx worker --poll-interval 5
```

Открыть `http://127.0.0.1:8080/` и пройти сценарий:

1. добавить, изменить и удалить координату;
2. импортировать и экспортировать справочник;
3. выбрать несколько точек и моделей;
4. задать горизонт и порог вероятности осадков;
5. создать задачу;
6. дождаться состояния `Завершено` либо увидеть понятную частичную ошибку;
7. скачать отдельный DOCX, манифест и ZIP;
8. повторить завершённую задачу;
9. отменить ожидающую задачу;
10. перезапустить API и убедиться, что справочник, задачи и артефакты сохранились.

Интерфейс должен работать без CDN, внешних шрифтов и JavaScript-библиотек.

## 4. Приёмка DOCX

Каждый документ проверяется в Microsoft Word и LibreOffice:

- открывается без восстановления;
- содержит титульный блок с координатами, высотой и часовым поясом;
- для каждой модели содержит ровно две прогностические таблицы;
- наглядная таблица содержит встроенные локальные PNG-пиктограммы;
- подробная таблица сохраняет все параметры выбранного профиля;
- заголовки таблиц повторяются на новых страницах;
- строки не разрываются между страницами;
- книжные и альбомные секции не повреждены;
- колонтитул и номера страниц отображаются;
- отсутствуют макросы и внешние изображения.

## 5. Приёмка автономного комплекта Astra Linux

Комплект собирается в среде, совпадающей с целевой Astra Linux по выпуску, архитектуре и `glibc`:

```bash
sudo bash scripts/build-astra-apt-repository.sh dist/apt-repository
bash scripts/build-offline-bundle.sh
```

На отключённой от сети контрольной машине:

```bash
sha256sum -c weather-to-docx-offline-*.tar.zst.sha256
tar --zstd -xf weather-to-docx-offline-*.tar.zst
cd weather-to-docx-offline-*
sudo ./install.sh
sudo ./doctor.sh
systemctl status weather-to-docx-api weather-to-docx-worker
```

Затем выполняются:

- автономный `sample`;
- создание задачи через веб-интерфейс;
- формирование DOCX worker-процессом;
- резервное копирование базы;
- обновление на следующий тестовый выпуск;
- проверка сохранности координат, шаблонов, задач и документов;
- откат на предыдущий выпуск.

Приёмка конкретной защищённой конфигурации Astra Linux считается отдельным стендовым испытанием: результат нельзя переносить между несовместимыми выпусками или архитектурами.

## 6. Критерий выпуска

Версия готова к выпуску, когда:

- CI проходит на поддерживаемых Python 3.11, 3.12 и 3.13;
- сквозной тест оператора проходит без сети;
- тестовый DOCX создаётся и открывается;
- реальные источники проходят сетевой дымовой тест;
- автономный комплект устанавливается на целевой стенд Astra Linux;
- обновление и откат не теряют пользовательские данные.
