# 🧱 Архитектура Weather to DOCX

## 1. Назначение

`weather-to-docx` получает прогнозы по координатам, сохраняет происхождение каждого ряда и формирует отдельный DOCX для каждого объекта. Архитектура разделяет четыре независимые области:

1. получение данных;
2. нормализацию и контроль качества;
3. формирование документов;
4. эксплуатацию в сетевом либо полностью закрытом контуре.

Главное ограничение: генератор DOCX никогда не читает JSON Open-Meteo или GRIB2 NOAA напрямую. Каждый адаптер обязан вернуть единую модель `ForecastSeries`.

## 2. Схема компонентов

```text
                         СЕТЕВОЙ КОНТУР

  Open-Meteo JSON ─────┐
  NOAA NOMADS GRIB2 ───┼──► SourceRegistry ──► ForecastSeries
  будущие адаптеры ────┘                           │
                                                   ├──► BatchService
                                                   │       ├──► DOCX
                                                   │       ├──► manifest.json
                                                   │       └──► ZIP
                                                   │
                                                   └──► ForecastBundle
                                                           │
                                                           ▼
                                                подписанный .tar.zst
                                                           │
                         ЗАКРЫТЫЙ КОНТУР                   ▼

  forecast-bundle.tar.zst ──► проверка подписи/SHA-256 ──► ForecastSeries
                                                                  │
                                                                  ▼
                                                            BatchService
```

## 3. Слои проекта

```text
src/weather_to_docx/
├── api/          HTTP API и выдача артефактов
├── document/     стили DOCX, пиктограммы и правила погоды
├── domain/       единая предметная модель и коды параметров
├── services/     пакетная обработка, очереди и переносные пакеты
├── sources/      адаптеры внешних источников
├── storage/      SQLite-очередь
├── utils/        единицы, ветер, пути и контрольные суммы
├── cli.py        операторские и служебные команды
└── settings.py   конфигурация через переменные WTD_*
```

### `domain`

Ключевые структуры:

- `Location` — координата, высота и часовой пояс объекта;
- `SourceMetadata` — поставщик, модель, продукт, цикл, разрешение и лицензия;
- `ForecastValue` — значение, единица, источник параметра и признак качества;
- `ForecastPoint` — один валидный срок;
- `ForecastSeries` — ряд одной модели для одной координаты;
- `BatchRequest` — координаты, источники и параметры документа;
- `BatchResult` — состояние задания и созданные файлы.

`ForecastValue.quality` принимает значения:

| Код | Смысл | Маркер в документе |
|---|---|---|
| `source` | исходное значение | нет |
| `calculated` | рассчитано из других полей | `*` |
| `interpolated` | интерполировано | `≈` |
| `corrected` | исправлено контролем качества | `†` |
| `stale` | устаревший цикл | `!` |
| `suspect` | сомнительное значение | `?` |
| `missing` | отсутствует | `—` |

### `sources`

Каждый источник реализует один интерфейс:

```python
async def fetch(
    location: Location,
    forecast_days: int,
    options: dict[str, Any] | None = None,
) -> ForecastSeries:
    ...
```

Регистрация выполняется в `SourceRegistry`. Добавление новой модели не должно требовать изменения генератора DOCX.

### `document`

`DocumentGenerator` создаёт:

- титульный блок объекта;
- отдельную секцию на каждую модель;
- компактную таблицу с локальными PNG-пиктограммами;
- подробную таблицу параметров;
- примечания о качестве и происхождении;
- колонтитулы и номера страниц.

Пиктограммы строятся `Pillow` и кэшируются локально. Внешние изображения и CDN не используются.

### `services`

`ForecastBatchService` изолирует сбои: ошибка одной модели или координаты не останавливает остальные результаты. После обработки создаются:

```text
<batch-id>/
├── Прогноз_<объект>_<дата>.docx
├── manifest.json
└── <имя-пакета>.zip
```

`ForecastBundle` переносит нормализованные ряды в изолированную сеть. Пакет подписывается Ed25519, а каждый файл проверяется по SHA-256.

### `storage`

Очередь реализована в SQLite с `WAL`, транзакционным захватом задания через `BEGIN IMMEDIATE` и состояниями:

```text
queued → running → completed | partial | failed
                  ↘ cancelled
```

Отдельный Redis/Celery для первого производственного варианта не требуется.

## 4. Происхождение данных

В каждый `ForecastSeries` записываются:

- `source_id`;
- организация-поставщик;
- модель и продукт;
- точный цикл, если источник его сообщает;
- время получения;
- горизонт и нативный шаг;
- разрешение и координаты модельного узла;
- лицензия и атрибуция;
- версия адаптера;
- предупреждения.

Прямой GFS хранит точный цикл. Open-Meteo/GFS явно маркируется как канал, где стандартный ответ не даёт точного времени исходного цикла.

## 5. Правила отказоустойчивости

- отсутствующее значение не заменяется нулём;
- модель не подменяется другой моделью;
- старый цикл не используется скрытно;
- детерминированная сумма осадков не называется вероятностью;
- неполный набор данных отмечается в манифесте;
- ошибки источника не разрушают уже полученные ряды;
- повторная генерация из автономного пакета не требует сети;
- документ воспроизводим по метаданным и хэшам исходного пакета.

## 6. Расширение системы

Новый адаптер должен:

1. определить `SourceDescriptor`;
2. получить данные без скрытой подмены модели;
3. привести единицы к внутренним;
4. заполнить `SourceMetadata`;
5. проставить `QualityFlag` рассчитанным величинам;
6. добавить фикстуру и тест разбора без Интернета;
7. зарегистрироваться в `SourceRegistry`;
8. быть описан в `docs/SOURCES.md`.

Будущие ECMWF, GEFS, ICON и GDPS должны подключаться именно этим способом.
