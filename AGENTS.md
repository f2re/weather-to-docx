# Обязательный контракт для кодовых агентов

Этот файл обязателен для Codex, GitHub Copilot, Claude Code, Gemini CLI и любых других автоматизированных исполнителей. Полный нормативный документ: `docs/DEVELOPMENT_CONTRACT.md`.

## Перед любым изменением

1. Получить актуальную `main` и зафиксировать её SHA.
2. Прочитать `pyproject.toml`, `VERSION`, `src/weather_to_docx/__init__.py` и верхнюю запись `CHANGELOG.md`.
3. Создать отдельную ветку от текущей `main`. Нельзя продолжать старую ветку без проверки, что она не отстаёт.
4. Прочитать относящиеся к задаче документы и тесты. Не заменять фактическое состояние предположениями.

## Контракт версии

- Каноническая текущая версия задаётся в `pyproject.toml`.
- Версия никогда не уменьшается.
- Версия не меняется без явного решения о выпуске.
- При изменении версии одновременно синхронизируются `VERSION`, `__version__`, User-Agent, текущие релизные маркеры и активная документация.
- В исходном коде запрещены отдельные жёстко заданные номера версии. Использовать `weather_to_docx.__version__`.
- Исторические разделы `CHANGELOG.md` и файлы вида `RELEASE_<старая версия>.md` не переписываются под текущую версию.
- Файловый маркер `docs/RELEASE_TAG.txt` не является реальным Git-тегом. Нельзя заявлять о наличии тега или GitHub Release без отдельной проверки GitHub API.

Обязательная команда:

```bash
python scripts/check-version.py
```

## Контракт реализации

- Не создавать прямые коммиты в `main`; использовать ветку и PR.
- Не удалять существующую функциональность и данные молча.
- Изменение поведения должно иметь тест, а исправление дефекта — регрессионный тест.
- Для DOCX и метеограмм обязательны структурная проверка и физический рендер, когда доступен LibreOffice/Poppler.
- Пользовательский документ сохраняет русские подписи и единицы; технические поля не возвращаются в основной отчёт без отдельного режима.
- Ошибка не скрывается фиктивным успехом. Частично выполненная работа описывается как частичная.

## Контракт доказательств

Запрещено писать «проверено», «CI зелёный», «слито», «выпущено», «тег создан» или указывать текущую версию по памяти.

Каждое такое утверждение должно опираться на фактический результат:

- статус GitHub Actions;
- SHA коммита или слияния;
- содержимое текущей `main`;
- список реальных тегов или релизов;
- вывод выполненной команды.

После слияния повторно получить `main`, проверить версию и сообщать именно merge SHA из GitHub.

## Обязательные проверки перед готовностью PR

```bash
python scripts/check-version.py
python scripts/check-development-contract.py
ruff check .
pytest
python -m compileall -q src
node --check src/weather_to_docx/static/app.js
node --check src/weather_to_docx/static/reliability.js
node --check src/weather_to_docx/static/compact_report.js
weather-to-docx-verify --deep
```

PR остаётся черновиком, пока обязательные проверки не завершены успешно. Нельзя сливать при `queued`, `in_progress`, `failure`, конфликте или отставании ветки от `main`.

## Критерий завершения

Работа завершена только когда:

1. реализованы заявленные требования;
2. добавлены или обновлены тесты;
3. контракты версии и разработки проходят;
4. CI полностью зелёный;
5. PR слит;
6. актуальная `main` повторно проверена;
7. итоговый отчёт содержит факты, ограничения и точный SHA.
